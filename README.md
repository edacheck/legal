# Едачек: публичные юридические документы

Публичные исходники и CI/CD для `legal.edacheck.ru` на GitHub Pages. Политика, соглашение и инструкция удаления собираются в читаемые HTML-страницы и PDF с одинаковым текстом. Утвержденная редакция `2026-10-28.1` действует с 28 октября 2026 года; ее статус и дата закреплены в `edition.json`.

## Локальная сборка

Требуются Python 3.12+, Pandoc 3.6.4, Typst 0.15.1, Poppler (`pdftotext`) и DejaVu Sans. Linux x86_64 binaries Pandoc и Typst можно установить только в `.tools/bin` через `make bootstrap`: архивы проверяются по закрепленным SHA-256. Системные пакеты локальная команда не устанавливает.

```sh
make lint
make test
```

Если использовался bootstrap, добавьте `.tools/bin` в PATH перед сборкой. Результат - `_build/site/index.html`. Это локальная ссылка на полностью проверенное поколение; при публикации переносится содержимое, а не сама ссылка.

Сборка сначала выполняется в staging. Ошибка конвертера или проверки сохраняет прежний комплект. Утвержденную редакцию нельзя менять под прежним номером. Неопубликованные проекты могут редактироваться.

## CI/CD

- PR, `dev` и рабочие ветки: проверка, регрессионные тесты и сборка артефакта без публикации.
- `main`: те же проверки, неизменяемый публичный snapshot и deployment GitHub Pages.
- Actions закреплены по commit SHA; Pandoc и Typst - по версии и SHA-256 архива.
- Внешние сборочные инструменты загружаются только в CI/bootstrap; сама конвертация не обращается к сети.
- Workflow имеет read-only token по умолчанию. Запись в Releases и Pages разрешена отдельным jobs только для `main`.

Каждый main-коммит сохраняет `site.tar.gz` в отдельном GitHub prerelease `site-<commit>`. Это технический snapshot сайта, не утверждение юридической редакции. Он сохраняет все прошлые версионные страницы вне краткоживущих Actions artifacts. Следующая сборка восстанавливает историю из snapshot; ошибки API или повреждение архива прерывают сборку. Повторная публикация того же коммита использует прежние проверенные байты.

Draft или неполный snapshot блокирует deploy; существующий опубликованный архив проверяется по содержимому. Сразу перед deployment повторно проверяется актуальный SHA `main`, поэтому повтор старого failed job не откатывает сайт после нового выпуска. Actions artifacts хранятся 7 дней; после их истечения нужно повторить весь workflow, восстанавливающий содержимое из постоянного snapshot.

Текущие страницы: `/privacy/`, `/terms/`, `/deletion/`. Для акцепта используются `/versions/<version>/privacy/` и `/versions/<version>/terms/`. PDF также ссылаются на конкретную редакцию. Папка `versions/` сохраняется при обновлении.

Фиксированная действующая редакция: `/versions/2026-10-28.1/`. Прежняя проектная редакция остается в архиве по собственному адресу; ее текст и статус не переписываются задним числом.

## Переменные приложения

`/versions/<version>/registration-links.json` содержит публичные значения:

```text
EDACHECK_REGISTRATION_AGREEMENT_URL
EDACHECK_REGISTRATION_POLICY_URL
EDACHECK_REGISTRATION_DOCUMENT_VERSION
EDACHECK_REGISTRATION_POLICY_VERSION
```

Их передают компилятору Flutter через существующий механизм Dart defines в GitLab CI приложения. Одного shell environment недостаточно. Точные встроенные тексты и их SHA-256 должны соответствовать той же редакции и серверному каталогу; этот репозиторий не меняет серверные настройки и приватные CI-переменные приложения. Проектные редакции не предназначены для production-акцепта.

Проверяемый public release handoff v1 генерируется только для утвержденной редакции:

```sh
make handoff HANDOFF_OUTPUT=/tmp/edacheck-registration-handoff.json
```

Committed `release-profile.json` фиксирует технические `document_id` и `action_id`. Выходной JSON содержит точные UTF-8 байты соглашения и политики в canonical Base64, SHA-256, версии и неизменяемые URL. Он является отдельным release handoff и записывается только за пределами репозитория.

## Git и резервная копия

Разработка: короткая рабочая ветка -> проверенный PR в `dev` с одним squash-коммитом -> свежая `release/*` -> проверенный PR в `main`. Публикация выполняется только из `main`.

Основной remote: `git@github.com:edacheck/legal.git`. Резервный: `ssh://git@gitlab.edacheck.ru:2222/foodapp/legal.git`. GitLab хранит копию Git-истории; Pages и сервисы там не разворачиваются. При резервном push используется `ci.skip`; force-push и удаление чужих refs не выполняются. GitHub Actions не получает пользовательский SSH-ключ для этого remote.

`make backup` копирует опубликованные GitHub-ветки `dev`, `main` и теги в настроенный remote `gitlab-backup`, используя локальный SSH-доступ. Это явная команда резервной синхронизации; автоматический job GitHub -> GitLab без отдельного deploy key не включен.

В этом репозитории находятся только публичные документы и сборка. Внутренние договоры, грантовые материалы и задачи из `foodapp-legal` сюда не включаются.
